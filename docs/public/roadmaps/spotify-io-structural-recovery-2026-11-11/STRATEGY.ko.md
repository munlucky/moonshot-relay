# Codex Reader·Writer 구조 개선 전략

> **대체됨:** 사용자의 I/O 범위 축소 지시에 따라 실행 기준은 [얇은 I/O 도구 리팩토링 작업 문서](./THIN_IO_REFACTOR_PLAN.ko.md)로 변경한다. 아래의 주장별 근거 계약·coverage·검토 패키지는 구현하지 않는다. 이 문서는 이전 검토 기록으로만 보존한다.

- 작성일: 2026-11-11 KST
- 검토 기준: `codex/spotify-io`, `d3603f8c` 및 v3 실행 산출물.
- 상태: 코드·기록 검토 및 개선 설계 완료. 아래 제품 변경과 신규 모델 실험은 미실행.
- 범위: 계정 설치형 일반 Codex의 대형 읽기와 참조 기반 신규 파일 생성. Kernel 없이 실행한다. 기존 파일 편집은 현재 Codex 경로를 유지한다.
- 유지: Luna 보조 호출, 기존 App Server, 기존 설치기, Kernel 전용 권한 검증, 사용자 파일 보호. DB·Queue·새 Router·영속 결과 캐시·검증 결과 재사용은 추가하지 않는다.

## 1. 판단

설치와 모델 분리는 해결됐다. 남은 핵심은 모델 능력만의 문제가 아니라 책임 배분과 주 모델의 왕복 구조다.

1. Reader는 의미 분석 외에 긴 원문을 정확히 재작성하고 유일한 위치까지 표현해야 한다. 근거 위치 선택과 원문 복사를 분리해야 한다.
2. Writer는 코드 생성만 위임한다. 요청 파일 작성, 메타데이터 재조회, 후보 전체 검토, 적용, 테스트를 주 모델이 계속 조립한다. 기계적인 처리를 Host로 이동해야 한다.
3. 품질 검토가 `semanticReview: REQUIRED` 또는 Skill 지침에 머문다. 주 모델이 제한된 근거로 판단할 수 있는 결과 계약이 부족하다.
4. 모델 호출 비용뿐 아니라 매 왕복에서 주 모델에 다시 들어가는 문맥 비용까지 줄여야 한다.

설치 기능을 다시 만들거나 인용 검사를 느슨하게 하는 방향은 채택하지 않는다. 구조를 바꿔도 경제성 달성은 새 실험으로 확인해야 한다.

## 2. 확인한 사실과 남은 불확실성

### 2.1 Reader

- 대량 Reader 9건은 모두 `host_io_citation_invalid`로 끝났다. 작은 계정 연결 시험의 성공과 구분한다.
- 현재 `locateFact`는 원문 내 존재, 인용의 유일성, 인용 내부의 심벌 일치를 하나의 오류로 묶는다.
- 정상 근거와 잘못된 근거가 섞여 있어도 한 항목의 실패로 전체 응답을 폐기한다.
- 최종 실패 결과에는 근거 번호·실패 조건·문제 범위가 없다. 확인한 영수증만으로 9건 각각의 실제 실패 원인을 복원할 수 없다.
- 따라서 9건 전부를 의미 오류 또는 공백 오류로 분류할 근거는 없다.
- 직접 읽기도 의미 검토와 별도 심벌 coverage 결과가 다르다. 기존 4/9 최종 통과 기록을 사후 수정하지 않는다.

### 2.2 Writer

원본 `w3-jobs/W*-*/receipt.json`과 주 모델 `main.jsonl`을 읽고 재합산했다.

| 주 모델 input | 732,480 | 2,470,448 |
| 주 모델 cached input, input의 부분집합 | 657,536 | 2,244,864 |

- 전체 토큰은 약 3.44배다. 캐시 입력을 제외해도 주 모델 input은 약 3.01배다.
- `W1-1-B`는 Skill/경로 확인, 참조 전체 읽기, 요청·생성, 메타데이터·후보 앞부분, 후보 뒷부분, 적용, 테스트의 7회 명령을 실행했다. 앞·뒷부분 열람으로 후보 대부분이 주 모델에 전달됐다.
- 이 기록은 중복 전달과 추가 왕복을 확인한다. 각 증가분을 Skill, 고정 문맥, 재읽기별로 정확히 귀속한 것은 아니다. 신규 계측으로 구분한다.
- 보고된 비용 +88.8%는 등록된 가정 요율의 결과다. 실제 가격·구독 차감량으로 해석하지 않는다.
- Writer 최종 9/9 통과에는 주 모델 수정이 포함됐다. Luna 단독 최초 생성 품질과 구분한다.

### 2.3 실험 범위

- 기존 W3 실행기는 양쪽 주 모델에 `--ignore-rules`를 사용한다. 일반 계정 새 세션 시험은 별도로 존재한다. 기존 경제성 수치가 모든 계정 문맥에서도 동일하다고 단정하지 않는다.
- 새 경제성 시험은 실제 기본 계정 문맥에서도 A/B를 맞춰 수행한다. 기존 결과를 무효화하거나 좋은 결과로 다시 쓰지 않는다.
- 설치·신뢰·Kernel 운영 Proof의 기존 완료와 보류는 그대로 유지한다. 이번 작업이 Kernel Windows/Linux Proof를 해결해야 하는 것은 아니다.

## 3. 목표 구조와 책임

```text
주 모델: 요구사항·범위·검토 기준 결정
  │ 한 번의 구조화 요청: 질문/명세 + 참조 경로 + 예산
  ▼
기존 Host I/O 진입점
  ├─ 경로·권한·해시 검사, 요청별 원문 스냅샷
  ├─ Luna 1회: 의미 분석 또는 신규 코드 생성
  ├─ Host: 근거 위치 검증·원문 추출·검토 자료 구성
  └─ 짧은 결과 + 미해결 항목 + 사용량
  ▼
주 모델: 근거와 필수 조건 검토
  ├─ Reader: 답변 또는 필요한 좁은 추가 조사
  └─ Writer: 기존 io-apply와 프로젝트 검증 실행
```

- Host는 파일 처리·해시·결과 형식·출력 예산을 책임진다.
- Luna는 근거를 선택하고 의미를 설명하거나 코드를 생성한다.
- 주 모델은 요구사항, 의미 정확성, 적용 판단, 필요한 수정을 책임진다.
- Host의 정확한 원문 추출은 의미 정확성의 증명이 아니다.
- 공통 코어와 standalone/Kernel 진입점 구분을 유지한다. Kernel 실패를 standalone으로 재시도하지 않는다.

## 4. Reader: 인용 재작성에서 원문 위치 선택으로

### 4.1 요청별 스냅샷과 근거 주소

Host가 현재 참조를 한 번 읽고 파일 해시와 행 번호를 붙여 Luna에 전달한다. 별도 색인 서비스나 영속 캐시는 만들지 않는다.

Luna의 응답은 자유로운 장문 인용 대신 다음 정보를 포함한다. 필드 이름은 기존 계약과 맞춰 구현한다.

```json
{
  "claims": [{
    "id": "c1",
    "text": "조건을 설명하는 문장",
    "evidence": [{"sourceId": "s1", "startLine": 20, "endLine": 28}],
    "uncertainty": "none"
  }],
  "unresolved": []
}
```

- `sourceId`는 Host가 해당 요청에서 발급한 참조 식별자다. 모델이 새 경로나 해시를 만들어 권위를 얻지 못한다.
- Host가 범위의 유효성을 검사하고 스냅샷에서 직접 인용을 추출한다. 동일 문장이 여러 곳에 있어도 위치가 지정되어 모호하지 않다.
- 인용에 함수 이름이 포함돼야 한다는 규칙은 제거한다. 함수 이름·범위가 필요한 과제에서는 선언과 조건 구간을 별도 근거로 연결한다.
- 심벌 소속을 기계적으로 확인하지 않았다면 검증 완료로 표시하지 않는다. 모든 언어를 지원하는 새 파서를 만들지 않는다.
- CRLF/LF·UTF-8 BOM·마지막 개행 처리 규칙을 고정한다. 원본 바이트 SHA와 행 계산용 표현을 구분하고 변환을 테스트한다.
- 반환 전 원본 신선도를 다시 확인한다. 파일이 바뀌면 오래된 근거를 현재 근거로 반환하지 않는다.

### 4.2 설명과 근거의 연결

- 근거와 무관한 독립 summary를 성공 답변처럼 반환하지 않는다. 반환하는 주장마다 검증된 근거 ID가 있어야 한다.
- 질문에 필수 항목이 이미 명시되어 있으면 선택적 `requiredItems`로 전달한다. Host는 응답 항목 누락만 검사하며 의미 충족을 자동 인증하지 않는다.
- 사실 하나가 잘못되면 실패한 항목의 ID·이유를 보존한다. 전체 JSON 파손, 권한 위반, 원본 변경은 요청 전체 실패다.
- 범위 오류인 항목은 유효한 주장과 분리해 진단 자료로 제공할 수 있다. 그 항목에 의존한 결론은 내보내지 않는다. 필수 항목이 남으면 전체 상태는 `incomplete`다.
- 정상 일부 근거를 반환하더라도 전체 과제 성공으로 집계하지 않는다. 부분 결과는 실패 분석과 좁은 추가 질문에만 사용한다.
- 근거 수·각 범위·총 인용 바이트를 요청 예산으로 제한한다. 범위가 너무 크면 잘라서 정답인 척하지 않고 명시적으로 거부 또는 불완전 판정한다.
- 의미 검토는 조건 AND/OR, 예외, 반환값, 호출 방향, 전체 coverage를 나눠 기록한다. 문구 `REQUIRED`만으로 완료 처리하지 않는다.

### 4.3 실패 진단

로컬 진단에는 항목 ID, 실패 단계, sourceId, 범위, 사용량을 기록한다. 필요한 원응답은 명시적 진단 모드에서 저장소 밖 요청 전용 디렉터리에 보관한다. 주 모델에는 짧은 오류만 반환한다. 일반 실행에서 전체 원문·원응답을 매번 출력하지 않는다.

## 5. Writer: 주 모델의 절차 조립을 Host 처리로 이동

### 5.1 요청 경로

- 기존 CLI에 stdin 등 구조화 입력을 추가해 임시 요청 파일을 주 모델이 별도 작성·조회하는 단계를 제거한다. 기존 명령을 확장하며 새 MCP 서버는 만들지 않는다.
- 주 모델은 사용자 요구와 이미 아는 사실로 명세를 작성한다. 참조 전체를 명세 작성 목적으로 다시 읽는 것은 기본 절차에서 제외한다.
- 요구가 불명확하면 필요한 구간만 조사한다. 의미 판단에 필요한 읽기를 금지하지 않는다.
- Host가 참조 바이트·해시·대상 검사·후보 저장·결과 저장을 한 호출 안에서 처리한다.
- 요청에 테스트 실행을 허용하지 않았다면 Host나 Luna가 임의로 코드를 실행하지 않는다.

### 5.2 검토 자료를 결과 계약에 포함

생성 응답은 후보 경로만이 아니라 주 모델이 다음 판단을 할 수 있는 제한된 자료를 제공한다.

- 후보 메타데이터: 경로, 해시, 크기, 참조 해시, 실제 모델 정보, 사용량.
- 변경 개요: 신규 파일, 주요 선언 또는 테스트명. Host가 추출 가능한 구조만 확정 정보로 표기한다.
- 요구별 근거: Luna가 제안한 요구 항목과 후보 내 범위. Host가 후보에서 해당 부분을 추출한다. 의미 충족은 주 모델이 판단한다.
- 필수 조건의 근거가 없거나 예산을 넘으면 `검토 미완료`로 표시한다. 전체 파일을 자동 반환하지 않는다.
- 테스트 결과가 없는 단계에서는 `NOT_RUN`이다. 모델이 적은 성공 문구를 테스트 결과로 수용하지 않는다.

Reader와 Writer는 동일한 스냅샷·범위 추출 함수를 재사용한다. 이 재사용은 Reader를 Writer 앞에 자동 호출하는 연쇄가 아니다. Writer 출력의 근거 범위가 틀렸다고 유효한 생성 후보와 사용량까지 잃지 않는다. 후보 상태와 검토 자료 상태를 분리한다.

### 5.3 왕복과 검증

- 정상 경로의 목표는 생성·검토 자료 반환 1회, 주 모델 검토 후 적용·프로젝트 테스트 1회다. Skill 최초 로딩과 필요한 의미 조사는 따로 계측한다.
- 적용과 기존 테스트는 한 기존 Codex 도구 호출에 묶을 수 있다. 적용이 실패하면 테스트를 실행하지 않는다. 테스트 실패를 명령 연결 방식 때문에 PASS로 숨기지 않는다.
- `io-apply`의 참조·후보 SHA, 경로 검사, `wx`는 유지한다. 일반 세션의 승인·범위를 우회하지 않는다.
- 테스트 결과는 짧은 합계와 실패 위치를 반환하고 전체 로그는 로컬에 둔다. 원본 exit code와 실행 명령을 남긴다. 무조건 성공하는 출력 요약기를 만들지 않는다.
- 테스트 통과만으로 의미 검토를 생략하지 않는다. 필요한 검토가 후보 전체를 요구하면 그 실행의 전체 열람 비용을 그대로 계산한다.
- 필요한 수정은 기존 정확 구간 편집을 사용한다. 자동 재생성·자동 재시도·별도 Reviewer 호출을 기본 경로에 넣지 않는다.

## 6. 결과·오류·임시 파일 수명

이 항목은 단순 청소가 아니라 생성 결과와 비용 증거가 함께 유지되는 계약이다.

- 호출 전에 요청 형식, 예산, 참조/대상, 메타데이터 목적지의 충돌·쓰기 가능성을 확인한다.
- 호출 후 저장 실패를 일반 생성 실패로 덮지 않는다. 후보 생성 상태, 저장 실패, 알려진 사용량을 분리해 반환한다. 가능한 출력 경로로 원래 결과를 유지하고 재생성을 지시하지 않는다.
- 결과 파일은 이 요청의 후보와 참조 해시를 연결하는 산출물이다. 별도 서비스·DB·전역 상태를 만들지 않는다.
- 성공 적용 후 본 요청이 만든 후보·중간 자료만 정리한다. 실패하거나 검토가 남은 후보는 진단 위치를 반환한다.
- 정리는 Host가 생성한 정확한 디렉터리와 소유 파일 목록에 한정한다. 외부에서 받은 임의 `candidatePath`의 부모를 재귀 삭제하지 않는다.
- 적용 부분 실패의 파일 상태를 보존한다. 사용자가 변경했을 수 있는 대상 파일을 자동으로 지우지 않는다.
- 프로세스가 죽은 뒤에도 전역 exactly-once를 보장하지 않는다. 이를 위해 Queue·분산 락을 추가하지 않는다.

## 7. 계측과 검증 전략

### 7.1 먼저 기록으로 원인을 분리

모델 실행 전후와 도구 경계에서 아래를 기록한다. 자료는 기존 로컬 실험 산출물 위치에 두고 canonical source에는 요약과 고정 시험만 둔다.

- 주 모델 요청 수와 제공되는 경우 요청별 input/cached/output. 누적 사용량은 차분 또는 최종값 중 한 방법으로 집계하여 이중 계산하지 않는다.
- 참조 원문, 후보 원문, 메타데이터, Skill, 테스트 로그 각각의 주 모델 전달 바이트.
- 한 후보를 여러 범위로 읽었을 때 범위의 합집합. 분할 열람도 전체 재읽기로 탐지한다.
- 생성, 검토, 적용, 테스트, 수정 단계의 시간. 합산 시간과 실제 전체 경과 시간을 구분한다.
- 정확한 실패 조건, 부분 성공, 수정 전 최초 품질, 수정 후 최종 품질.
- helper 시작 비용은 측정 대상이다. 고정 프롬프트가 크다는 추정만으로 별도 transport나 지속 세션을 만들지 않는다.

### 7.2 단계적 검증

1. **결정적 단위 시험:** 반복 인용, 함수 이름이 없는 조건부 구간, 다중 파일, 잘못된 범위, CRLF/BOM, 원본 변경, 부분 근거, metadata 실패. 모델 호출 없이 새 계약을 검증한다.
2. **작은 실모델 검증:** 기존 대량 실패 과제 하나와 Writer 과제 하나로 구조가 실제 동작하는지 확인한다. Reader는 주장의 의미와 coverage, Writer는 전체 재읽기·왕복 감소를 확인한다. 실패하면 원인을 고친 뒤 해당 경로만 재검증한다.
3. **전체 비교:** 통과한 구현을 고정한 뒤 기존 세 과제씩 A/B 3회, 순서 교차, 동일 주 모델·요구·원본·품질 Gate로 비교한다. 15% 비용 감소·25% 이내 시간 증가 기준은 유지한다. 실패·수정·검증 비용을 포함한다.
4. **실제 계정 확인:** 기본 계정 설정에서 설치본 E2E를 수행한다. 설치본과 실험본의 차이가 결과에 영향을 주면 해당 비교를 실제 설정으로 다시 수행한다. `--ignore-rules` 시험을 기본 계정 경제성으로 표시하지 않는다.

새 Reader 프로토콜은 인용 표현이 달라진다. 새 평가에서는 양쪽에 동일한 근거 정확성·필수 항목·의미 기준을 적용한다. 과거의 '인용 안에 심벌 이름 포함' 형식 결과를 의미 품질과 구분하되 과거 영수증은 수정하지 않는다. 평가 기준은 새 호출 전에 고정한다.

경제성은 과제별로 먼저 판정한다. 집계는 사전 등록된 과제별 동일 가중으로 보고하며, 일부 과제의 이득으로 실패 과제를 기본 채택하지 않는다. A/B 모두 필수 품질을 통과한 범위에서만 비용 우위를 주장한다. 실패 비용은 완료당 비용 계산에 포함하고 실패 수를 별도로 남긴다. 완료가 없으면 비용 우위를 정의하지 않는다.

## 8. 실행 순서와 파일 범위

| 단계 | 변경 내용 | 주요 위치 | 종료 조건 |
| --- | --- | --- | --- |
| S0 | 기존 결과 고정, 현재 기본 채택 보류를 Skill에 명시, 계측 분리 | Writer Skill, 기존 평가 코드 | 과거 결과 보존, 측정 경계 확정 |
| S1 | Reader의 스냅샷·범위 선택·주장별 근거 계약 | `io-reader.ts`, 필요한 공통 helper, focused tests | 기존 실패 유형 진단 가능, 새 의미·근거 시험 통과 |
| S2 | stdin 입력·기계적 준비 통합·Writer 검토 자료 | `moonshot-io.ts`, `io-writer.ts`, `io-standalone.ts`, Writer Skill | 일반 성공 경로 왕복 감소, 주 모델 전체 재읽기 없는 품질 통과 사례 |
| S3 | 결과 보존·적용·요청 소유 파일 수명 | 같은 CLI/standalone 경로 | 실패 시 사용량·후보 보존, 사용자 파일 불변 |
| S4 | frozen A/B, 기존 설치기 갱신, 새 계정 세션 확인 | 기존 installer/fixtures/guideline | 기능·품질·경제성·설치 독립 보고 |

- S0의 Writer 제한은 경제성 개선 전의 임시 운영 조치다. 사용자 명시 위임 또는 개선 실험에는 사용한다. 최종 목표를 영구 수동 호출로 축소하지 않는다.
- S1~S3는 공통 기능을 수정하므로 기존 Kernel I/O와 도구 금지 회귀를 수행한다. 새 Kernel 제품 Proof와 Owner 운영 체계는 이 범위에 추가하지 않는다.
- 모델 이름은 기존 Host 정책에서 선택한다. Hook·Skill·프로젝트별 예외에 중복 하드코딩하지 않는다.
- 일반 정상 경로가 계측상 단순해졌는지 확인한다. 함수 수나 코드 줄 수가 줄었다는 이유만으로 구조 개선 완료를 선언하지 않는다.

## 9. 선택하지 않는 대안

| 대안 | 제외 이유 |
| --- | --- |
| 인용의 fuzzy match로 성공률 증가 | 잘못된 원문을 받아들일 수 있고 의미 검증 문제도 해결하지 못함 |
| Skill에 '다시 읽지 말 것'만 추가 | 판단에 필요한 자료가 없으면 재읽기는 다시 발생함 |
| 모든 후보를 별도 AI Reviewer로 검증 | 호출·문맥 비용을 추가하며 독립 품질과 경제성이 미입증 |
| Reader→Writer 강제 연쇄 | 생성 전에 추가 비용과 의미 오류 전파를 만듦 |
| 로컬 캐시·세션 풀·검증 재사용부터 추가 | 현재의 최초 호출 실패와 주 모델 왕복 원인을 해결하지 못함 |
| 15% 기준을 낮춰 채택 | 실행 구조가 개선되지 않고 기존 실패를 감춤 |
| 모든 shell 읽기·편집 차단 | Spotify 최소 범위를 벗어나며 정상 개발과 필수 검토를 막음 |

## 10. 최종 보고 기준

다음 네 상태를 항상 분리한다.

1. 기능: 설치된 일반 세션에서 Luna가 실제 작업을 수행했는가.
2. 품질: 근거 위치, 필수 항목, 의미, 정상·결함 검사가 충족됐는가.
3. 경제성: 전체 작업 비용과 시간이 사전 기준을 충족했는가.
4. 운영: 계정 설치·Hook 상태·기존 Kernel 회귀가 확인됐는가.

구조 변경의 성공 기준은 'Luna 호출이 가능함'이 아니라 '동일 품질을 유지하면서 주 모델이 반복 수행하던 절차와 원문 전달이 실제로 줄어듦'이다. 경제성이 부족하면 기능 구현은 보존하고 해당 범위의 기본 채택은 계속 보류한다.
