# Spotify식 토큰 절감을 위한 얇은 I/O 도구 리팩토링 작업 문서

- 작성일: 2026-11-11 KST
- 구현 기준: `codex/spotify-io`, `d3603f8c`.
- 문서 상태: 작업 명세. 이번 작성에서는 제품 코드·계정 설치·모델 실험을 변경하지 않았다.
- 우선순위: 사용자의 최신 지시인 **I/O 대체에 집중, 응답 전체 폐기 제거, I/O 외 검증 기능 확대 금지**를 적용한다.
- 이 문서는 v3의 설치·권한·모델·계측 자산을 유지하며 Reader 반환 및 일반 세션 Writer 호출 절차를 개정한다. 앞선 `STRATEGY.ko.md`의 주장별 근거 계약·coverage·검토 패키지 제안은 채택하지 않는다.

## 1. 목표와 완료 범위

**주 모델이 대량 원문을 읽거나 신규 코드 전체를 출력하는 비용을 Luna 호출로 대체한다.** 일반 Codex 세션에서 계정 설치본으로 실행하며 Kernel Run·Step을 만들지 않는다.

```text
Reader: 질문 + 파일 경로 → Host가 원문 전달 → Luna 답변 → 주 모델
Writer: 명세 + 참조 + 새 대상 → Host가 참조 전달 → Luna 코드 → Host가 새 파일 저장
```

Writer는 주 모델에 긴 코드를 반환하지 않는다. Reader는 인용 형식이 맞지 않는다는 이유로 유용한 답변 전체를 버리지 않는다. 필요한 프로젝트 검토·테스트·수정은 원래 Codex 작업 흐름에서 수행한다.

대상은 대형 읽기와 참조 패턴이 있는 신규 파일 생성이다. 작은 파일, 정확 검색, 범위 읽기, 기존 파일 편집은 현재 도구를 사용한다. 모든 파일 I/O를 가로채거나 모든 개발 작업을 Luna에 맡기는 계획이 아니다.

## 2. Spotify 원본과 현재 구현의 차이

Spotify의 공개 스크립트는 Reader에서 질문과 파일을 모델에 전달하고 답변을 반환한다. Writer는 명세·참조를 전달하고 대상 경로가 있으면 생성 결과를 파일에 쓴다. Writer Skill은 필요한 검토·부분 수정을 주 모델의 작업으로 남긴다.

우리 구현은 이 흐름에 다음 비용을 추가했다.

| 현재 코드/절차 | 문제 | 이번 결정 |
| --- | --- | --- |
| Reader `facts` 필수, 인용 유일성·심벌 포함 검사 | 답변 내용과 인용 형식의 성공을 결합 | 기본 Reader 경로에서 제거 |
| 하나의 인용 실패로 전체 `failed` | 유효한 답변까지 잃고 재읽기 유발 | 답변 보존; I/O 실패와 구분 |
| `semanticReview: REQUIRED` | 별도 검증 워크플로로 오해 가능 | 도구 완료 조건에서 제거 |
| 요청 파일 작성·후보 metadata 재조회·별도 적용 | 주 모델이 기계적 절차를 조립 | stdin 요청 + standalone 생성·저장 단일 호출 |
| 후보를 나눠 전체 재열람 | 위임 출력이 다시 주 모델 입력으로 들어감 | 의무 절차 제거; 필요한 검토만 기존 도구로 수행 |
| 앞선 전략의 요구별 검토 패키지 | 새로운 분석·검증 기능 확대 | 구현하지 않음 |

원본의 쓰기 방식까지 그대로 복사하지는 않는다. 기존 파일 보호를 위한 `wx`, 경로·원본 변경 검사는 기존 함수로 유지한다. 이들은 파일 I/O 처리 조건이며 별도 제품 품질 심사 기능이 아니다.

## 3. 제품 기능·작업 검증·실험을 분리한다

| 구분 | 책임 | 두지 않을 기능 |
| --- | --- | --- |
| I/O 도구 | 입력 취득, Luna 호출, 응답 전달, 신규 파일 저장, 오류·사용량 반환 | 의미 판정, 요구사항 coverage 인증, 자동 테스트/수정 |
| 기존 Codex 개발 작업 | 요구 판단, 필요한 내용 확인, 프로젝트 테스트, 수정 | 위임을 썼다는 이유만으로 추가하는 별도 검토 절차 |
| 리팩토링 검증 | I/O 계약·회귀·품질·경제성 평가 | 실험용 mutation/oracle를 운영 도구에 내장 |

평가에서 의미와 품질을 확인하는 것은 필요하다. 그 평가 절차를 Reader·Writer의 새 기능으로 구현하지 않는다. 검사 실패는 실제로 부족한 항목에 기록한다. 테스트가 빠졌다는 이유로 모델 호출·파일 저장 자체를 미구현으로 바꾸지 않는다.

## 4. 유지·제거·축소 목록

### 유지

- 기존 Host 모델 정책과 실제 Luna 식별. 주 모델 변경과 별개로 보조 모델을 선택한다.
- 현재 도구 금지 App Server 호출과 종료 확인. Luna에 shell·파일 적용 권한을 주지 않는다.
- 경로 경계, 입력 크기·시간 제한, 참조 SHA, 기존 파일 덮어쓰기 방지.
- standalone와 Kernel 호출 경계. Kernel 요청은 기존 Run·Step·Worktree·Owner 권위를 거친다.
- 기존 계정 설치기와 사용자 Hook 보존·갱신·복원.
- 전체 작업 사용량·시간 계측. 기존 실패 결과 보존.

### 제거 또는 기본 경로에서 제외

- Reader의 `facts`·unique quote·인용 내부 symbol을 강제하는 성공 조건.
- 모든 주장에 검증된 근거 ID를 요구하는 계약, 필수 coverage 엔진, 의미 검토 완료 상태기계.
- Writer 호출 전 전체 참조 읽기와 생성 후 전체 후보 읽기를 의무화한 절차.
- 일반 세션에서 생성과 적용 사이의 필수 metadata 파일 조회·승인 왕복.
- 검토 패키지, 별도 AI Reviewer, 자동 Reader→Writer 연쇄, 자동 재생성·재시도.
- 새 Router, MCP 서버, DB, Queue, Scheduler, AST 범용 분석기, 로컬 결과 캐시.

## 5. Reader 작업 명세

### 5.1 응답을 단순화한다

`createIoReader`의 기본 모델 출력은 **질문에 대한 짧은 텍스트 답변**으로 한다. 강제 `{summary,facts}` 출력 스키마와 `locateFact` 성공 검사를 제거한다. 프롬프트는 질문, 원문 경계, 조건·예외 보존, 불확실성 표현에 집중한다.

Host가 외부에 반환하는 JSON 봉투는 유지할 수 있다. 모델에게 그 봉투를 생성시키지 않는다.

```json
{
  "status": "answered",
  "answer": "질문에 대한 짧은 답변",
  "sources": [{"path": "src/example.ts", "sha256": "sha256:..."}],
  "requestedModel": "<Host 선택값>",
  "resolvedModel": "<App Server 보고값>",
  "usage": {}
}
```

- `sources`는 Host가 실제로 전달한 파일 목록이다. 답변의 각 주장이 증명됐다는 표시가 아니다.
- 모델이 답변에 행 번호나 인용을 포함할 수 있으나, 이를 기계 검증된 근거로 표시하지 않는다.
- 답변에 코드 인용이 없거나 함수 이름이 빠져도 반환한다. 답변의 부정확성은 개발 작업·평가에서 다룬다.
- 자동 인용 보정기·fuzzy matcher·행 선택 프로토콜을 새로 만들지 않는다. 정확 구간이 필요하면 주 모델이 기존 도구를 사용한다.

### 5.2 응답 보존과 실패의 구분

| 상황 | 처리 |
| --- | --- |
| 정상 답변, 불완전한 인용·출처 표현 | 답변 보존, 인용 때문에 전체 실패 처리하지 않음 |
| 빈 응답 또는 모델 호출 실패 | 실패 반환, 관측한 사용량·오류 유지; 없는 답변을 합성하지 않음 |
| 반환 크기 초과 | 예산 내 preview와 `truncated` 상태를 반환; 완전한 답변으로 표시하지 않음 |
| 응답 수신 후 원본 변경 | 수신 답변을 `stale` 진단으로 보존; 현재 원문에 대한 정상 답변으로 표시하지 않음 |
| 권한 밖 경로·금지 도구 이벤트 | 기존 실행 거부 유지; 해당 내용을 정상 답변으로 노출하지 않음 |
| 선택적 결과 파일 저장 실패 | 이미 받은 답변과 사용량을 가능한 stdout 결과에 포함하고 저장 실패를 별도 표시 |

`answered`, `stale`, `truncated`, `failed`는 짧은 결과 분류다. 영속 상태기계가 아니다. 반환 제한을 지키면서 받은 유용한 내용을 보존한다. transport가 반환하지 않은 원응답을 복원한다고 약속하지 않는다.

### 5.3 Hook

현재 단순 전체 읽기 감지 범위를 유지한다. 작은 읽기·검색·부분 읽기는 통과시킨다. Hook은 호출법을 짧게 안내하며 Luna를 직접 실행하지 않는다. 새 CLI 입력 방식에 맞게 안내만 갱신한다. 모든 shell 표현을 해석하는 범용 가로채기는 추가하지 않는다.

## 6. Writer 작업 명세

### 6.1 일반 Codex의 생성·저장을 한 호출로 끝낸다

기존 `io-write`에 **명시적 `--apply` 옵션**을 추가한다. 사용자가 새 파일 생성을 요청한 일반 Codex 세션에서 이 경로를 사용한다. 구현은 기존 생성 함수와 `applyStandaloneIoCandidate`를 같은 프로세스 안에서 순서대로 호출하는 수준으로 제한한다.

```text
주 모델: 명세 + 참조 경로 + 새 파일명 지정
  → 기존 io-write --apply
      → Host: 참조·목적지 확인
      → Luna: 코드 생성 1회
      → Host: 기존 격리 후보 생성 + 기존 SHA/경로 검사 + wx 저장
  ← created + 파일명·크기·해시·모델·사용량
```

- 생성 요청 자체가 지정한 새 파일 저장을 포함한다. 추가 제품 승인 절차를 만들지 않는다. 기존 Codex 도구 권한·승인 정책은 따른다.
- 중간 후보는 Host 내부 산출물로 사용한다. 정상 성공 시 주 모델이 후보 metadata를 읽고 다시 `io-apply`를 호출할 필요가 없다.
- 대상은 명세에서 지정한 신규 파일 하나다. 기존 파일 편집, 다른 파일 생성, 자동 수정·재생성은 수행하지 않는다.
- 적용 전 후보·참조 SHA·경로 검사와 `wx`는 기존 함수를 재사용한다. 생성 후 대상이 생기거나 원본이 바뀌면 덮어쓰지 않는다.
- 결과가 저장됐다는 뜻은 `created`이며, 코드가 정확하거나 테스트를 통과했다는 뜻은 아니다.
- 주 모델에 생성 코드 전체를 출력하지 않는다. 파일명·해시·크기·실행 결과만 반환한다.

### 6.2 기존 후보 경로와 Kernel

- 기존 후보 생성과 `io-apply`는 Kernel 또는 명시적으로 후보만 원하는 호출에 계속 사용한다. 일반 세션의 기본 Skill 절차에서는 분리 호출을 요구하지 않는다.
- Kernel Writer에는 `--apply` 동작을 연결하지 않는다. Kernel bound wrapper는 후보 반환 뒤 기존 Proof·Owner 적용 경로를 따른다.
- `createIoWriter`의 기존 `{path,code}` 파싱은 파일 바이트를 추출하는 I/O 형식 검사로 유지한다. 인용·coverage·의미 판정과는 다른 검사다.
- 형식 오류가 난 모델 출력을 임의로 코드라고 해석해 대상에 쓰지 않는다. 이미 받은 결과와 사용량은 제한된 진단으로 보존하며 자동 재생성하지 않는다.

### 6.3 Writer Skill을 줄인다

Skill의 정상 절차는 다음 세 항목으로 제한한다.

1. 생성 대상·명세·기존 참조를 정한다. 전체 코드를 주 모델이 먼저 생성하지 않는다.
2. 설치된 `io-write --apply`를 구조화 입력으로 한 번 호출하고 저장 결과를 확인한다.
3. 원래 프로젝트 작업에서 필요한 검토·테스트·부분 수정을 수행한다.

명세 작성만을 위한 전체 원문 재읽기, 의무 전체 후보 검토, 요구별 검토 패키지 작성은 넣지 않는다. 필요한 내용 확인은 허용하고 그 비용을 집계한다. 모든 결과를 무검토로 신뢰하라는 지침도 넣지 않는다.

## 7. CLI와 결과 처리

- 기존 `moonshot-io` 진입점을 유지한다. `requestFile` 자리에 `-`를 받아 stdin JSON을 읽도록 확장한다. 기존 파일 입력도 유지한다.
- 예시 계약: `node <installed>/bin/moonshot-io.mjs io-read -`, `node <installed>/bin/moonshot-io.mjs io-write - --apply`. 정확한 도움말·파싱·설치 안내는 같은 변경에서 일치시킨다.
- 입력 예산·timeout은 기존 검증을 유지한다. 주 모델이 매번 새로운 정책을 설계하도록 추가 필드를 만들지 않는다.
- 선택적 metadata 출력 경로는 호출 전 확인한다. 사전 확인 뒤의 경합·저장 오류도 고려해 생성 결과와 usage를 일반 오류로 덮어쓰지 않는다.
- `--apply`에서 생성 성공·저장 실패가 발생하면 후보 위치, 실제 목적지 상태, 오류, 알려진 usage를 함께 반환한다. 재생성 없이 원인을 판단할 수 있어야 한다.
- 정상 적용 후 해당 호출이 만든 후보만 정리한다. 실패 후보는 진단 위치를 반환하고 자동 재시도하지 않는다. 임의 경로의 부모를 재귀 삭제하지 않는다.
- 기존 `createIoInvocation.evidence()`의 Kernel 전용 완료 필드는 Kernel 어댑터에 남긴다. 일반 CLI에는 `hostProductProof`, `ownerDelivery`, `kernelDone` 같은 무관한 필드를 기본 출력하지 않는다. 생성·사용량 관측을 복제 구현하지 말고 출력 경계에서 구분한다.
- 테스트 실행기, 테스트 로그 요약기, 프로젝트 명령 탐색기를 I/O CLI에 추가하지 않는다. 기존 Codex 도구로 테스트한다.

Reader의 반환 필드 변경은 실제 소비 코드·테스트·설치본을 함께 갱신한다. 예전 `evidence-ready`를 검증된 근거인 것처럼 위장하거나 빈 evidence를 채워 통과시키지 않는다. 기존 Kernel 실행 권한·Report·Owner 계약의 변경과 혼동하지 않는다. 별도 영구 v1/v2 실행 엔진은 만들지 않는다.

## 9. 실행 순서

| 단계 | 작업 | 종료 조건 |
| --- | --- | --- |
| T0 | 현재 checkout·설치 상태·기존 결과 확인, 실제 소비 코드 검색 | 변경 범위 고정. 이미 완료된 설치를 재개발하지 않음 |
| T1 | Reader 텍스트 응답과 실패 보존 | 인용 형식 때문에 답변 전체를 잃지 않음. 무관한 의미 검사 없음 |
| T2 | stdin 및 standalone Writer 생성·저장 단일 호출 | 1회 호출로 파일 생성, 전체 코드 stdout 미반환, 기존 파일 보호 |
| T3 | Hook 안내·Skill·설치본 갱신과 회귀 | 새 일반 세션에서 두 기능 사용. Kernel 권한 유지 |
| T4 | 품질·왕복·전체 비용 비교 후 채택 판단 | 기능·품질·경제성·설치 상태를 각각 보고 |

T1/T2는 기존 함수의 책임 이동과 삭제를 우선한다. 범용 인터페이스 계층이나 새로운 작업 상태를 먼저 만들지 않는다. 현재 실패 한 건을 해결하려고 프로젝트명·특정 함수·언어별 정책을 shared harness에 추가하지 않는다.

## 10. 필요한 검증과 수용 조건

### 10.1 도구 계약 시험

- Reader 답변에 인용 없음, 동일 인용 반복, 함수명 없음: 정상 답변 반환.
- Reader 빈 응답·너무 긴 응답·수신 후 원본 변경: 정해진 상태·예산·사용량 유지. 정상 답변으로 오인하지 않음.
- Writer stdin → Luna 1회 → 새 파일 생성 → 짧은 결과 반환. 주 모델의 별도 metadata 조회·io-apply 호출이 없어도 완료.
- Writer 기존 대상·참조 변경·후보 변경·부모 링크·동시 생성·쓰기 실패: 기존 보호 유지, 원본 보존, 상태·usage 반환.
- 선택적 metadata 저장 실패: 이미 생성한 결과와 비용 정보가 최종 오류에서 사라지지 않음.
- 일반 세션에서 Kernel Run 없이 동작. Kernel 경로는 기존 권한 실패를 standalone으로 우회하지 않음.
- 설치·업데이트 후 개인 설정·다른 Hook·Skill 보존.

### 10.2 실사용 품질 시험

기존 과제의 질문·요구·소스와 정상/결함 사례를 사용한다. Reader는 답의 조건·예외·필수 내용 정확성을 평가하고 Writer는 기존 프로젝트 테스트와 필요한 검토로 평가한다. 평가 로직을 제품에 탑재하지 않는다.

Reader의 과거 인용 형식 기준은 **새 평가의 도구 성공 조건에서 제거**한다. 직접 경로와 위임 경로 모두 같은 내용 정확성 기준을 적용한다. 변경 기준은 새 호출 전에 고정하고, 기존 9회 실패·직접 경로 4/9 기록은 수정하지 않는다. '답변 반환 성공'과 '답변 정확성 통과'를 별도로 집계한다.

### 10.3 토큰·시간 비교

1. 먼저 Reader 한 과제, Writer 한 과제로 전체 반환·저장과 불필요한 왕복 제거를 확인한다. 실패한 구조로 대규모 실험을 반복하지 않는다.
2. 통과한 구현을 고정한 뒤 기존 Reader 세 과제·Writer 세 과제, 각 A/B 3회로 비교한다. 순서를 교차하고 같은 주 모델·계정 설정·요구·테스트를 사용한다.
3. 주 모델 input/cached/output, helper input/output, 도구 호출 수, 원문·후보 전달량, 실제 완료 시간, 실패·수정 비용을 포함한다. cached input을 전체 input에 다시 더하지 않는다.
4. 이전 W3의 `--ignore-rules` 결과와 실제 기본 계정 결과는 구분한다. 새 채택 판단은 적용할 계정 실행 조건에서 측정한다.
5. v3의 비용 15% 이상 감소·시간 증가 25% 이하 기준을 유지한다. 이는 사전 가정 요율의 환산 지표이며 실제 구독 차감이 아니다. 전체 토큰·주 모델 토큰 감소는 별도 보고한다.
6. 과제별로 먼저 판정한다. 실패·재작업 비용을 포함하고 완료가 없으면 완료당 절감률을 계산하지 않는다. usage 누락은 해당 경제성 판정 보류다.

정상 경로의 목표는 Reader 1회 I/O 호출, Writer 생성·저장 1회 I/O 호출이다. Skill 최초 로딩, 원래 필요한 테스트·편집·추가 질문까지 포함한 실제 작업 비용도 따로 집계한다. 왕복 수를 맞추기 위해 필수 검토를 숨기지 않는다.

### 10.4 최종 판정

- **기능 구현:** Luna Reader 답변 반환과 Writer 파일 저장이 일반 계정 세션에서 동작.
- **품질:** 동일 과제의 요구·조건·테스트 기준 통과.
- **경제성:** Reader/Writer 각각 사전 기준 통과 여부 보고.
- **설치:** 실제 계정 설치본과 검증 코드 일치, 새 세션 재현.

경제성이 부족해도 구현 사실을 취소하지 않는다. 그 범위의 기본 채택을 보류한다. 개선 검증 전 현재 Reader Hook의 비활성 상태를 임의로 바꾸지 않는다. Writer 역시 미채택 상태에서는 명시적 위임·시험 범위로 안내하고, 통과한 범위만 정상 Skill 선택 대상으로 전환한다.
