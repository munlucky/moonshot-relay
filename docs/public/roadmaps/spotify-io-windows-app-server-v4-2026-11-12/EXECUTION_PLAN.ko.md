## 1. 최종 목표

Windows에서 Codex App Server를 정확하게 실행하고 종료하는 결함을 수정한다.

수정된 실행 경로를 실제 일반 Codex 개발 작업에서 사용해 다음을 증명한다.

1. Reader가 대형 파일 읽기를 Luna에 위임하고 주 모델에는 필요한 결과만 전달한다.
2. Writer가 Luna로 신규 파일을 생성·저장하고 코드 전체를 주 모델에 반환하지 않는다.
3. 위임 이후 주 모델이 원래 개발 과제를 완료하고 동일한 수용 기준을 통과한다.
4. 주 모델과 Luna의 실제 입력·출력·재작업을 구분해 I/O 대체 여부를 확인한다.

**이번 작업의 완료 조건은 A01\~A08이다.**

기존 경제성 평가인 A09는 별도 채택 조건으로 유지한다. 이번 수정만을 이유로 전체 A/B 평가를 다시 실행하지 않는다.

### 구현하지 않을 기능

- 검증 전용 제품 API·CLI·실행 엔진
- 새 Router·DB·Queue·Scheduler
- 별도 프로세스 관리 플랫폼
- 결과 캐시 및 검증 결과 재사용
- 별도 Reviewer·검증 패키지
- 특정 테스트에만 동작하는 제품 분기
- 경제성 확보를 위한 새로운 모델 라우팅 정책

모의 서버와 PID 관측 코드는 기존 회귀 테스트에만 사용한다.

## 3. S1 — App Server 직접 실행 및 종료 수정

**주요 제품 변경 대상**

`src/host/kernel/codex-app-server-transport.ts`

### 3.1 활성 설치본의 네이티브 실행 파일 선택

기본 실행 파일은 transport에 전달된 `env`의 실제 실행 경로를 기준으로 선택한다.

- `PATH`와 Windows 명령 탐색 규칙으로 활성 Codex 확인
- 해당 설치본의 패키지 메타데이터 확인
- 동일 설치본의 네이티브 `codex.exe` 선택
- `shell:false`로 직접 실행
- 기존 명시적 실행 파일 지정 계약 보존
- 실행 파일을 확인할 수 없으면 명시적 실패

다른 설치본이나 `.cmd`로 자동 전환하지 않는다.

사용자 홈 경로, Codex 버전 및 플랫폼 패키지 경로를 고정값으로 사용하지 않는다.

### 3.2 필수 실행 환경 보존

현재 설치된 Codex 런처가 설정하는 다음 값과 실행 환경을 확인한다.

- `CODEX_MANAGED_PACKAGE_ROOT`
- 실제 패키지 관리자에 대응하는 `CODEX_MANAGED_BY_*`
- 인증·환경변수 전달
- 기존 모델·effort·Sandbox 설정

직접 실행에 필요한 값만 구성하고 런처 전체 로직은 복제하지 않는다.

### 3.3 정확한 종료 확인

기존 `stopOwnedAppServer()`와 `close()`를 재사용한다.

필수 조건:

- 실제 소유한 App Server 프로세스의 종료 확인
- 종료와 stdout/stderr drain 구분
- 초기화 실패·timeout에서 안전한 정리
- 반복 `close()` 결과 일관성
- 늦게 도착하는 도구 실행 이벤트 차단
- 종료 미확인 시 성공 반환 금지
- `writerExitVerified:false` 유지

임의의 프로세스 트리를 강제 종료하거나 별도 OS 프로세스 관리 시스템을 도입하지 않는다.

### 완료 조건

네이티브 App Server가 실제 종료된 경우에만 `appServerExited:true`를 반환한다. 셸 종료를 App Server 종료로 취급하는 경로가 없어야 한다.

## 4. S2 — Windows 실행·종료 및 Reader·Writer 회귀 검증

### 필수 테스트

| ID  | 시험               | 기대 결과               |
| --- | ---------------- | ------------------- |
| T01 | 활성 설치본 선택        | 전달된 `env`와 실행 버전 일치 |
| T02 | 네이티브 실행          | `shell:false` 직접 실행 |
| T03 | 실행 환경 보존         | 필수 Codex 환경변수 유지    |
| T04 | no-tools 정상 Turn | 정상 응답·종료·drain      |
| T05 | 서버 종료 후 PID 확인   | 실제 소유 서버 종료         |
| T06 | 초기화 실패·timeout   | 거짓 성공 없음            |
| T07 | 반복 `close()`     | 종료 결과 일관성           |
| T08 | 늦은 도구 이벤트        | 기존 차단 유지            |
| T09 | 실행 파일 없음·실행 실패   | 명확한 오류, 자동 우회 없음    |
| T10 | Reader·Writer 회귀 | 응답·저장·파일 보호 유지      |

### 검증 방법

**첫째, 모의 App Server**

기존 테스트에 no-tools Turn, 종료, timeout, drain 및 프로세스 잔존 반례를 추가한다.

**둘째, 실제 설치된 Codex**

기본 resolver가 선택한 Codex로 `initialize → config/read → 종료`를 실행한다.

모델 Turn은 사용하지 않는다. 실행 파일 선택과 실제 서버 종료를 검증한다.

**셋째, 기존 기능 회귀**

Reader·Writer standalone 테스트, App Server 집중 회귀 및 영향을 받는 Kernel 테스트를 수행한다.

Windows 필수 테스트를 우선 완료하고, Linux/macOS 영향 검증이 불가능하면 해당 환경만 `NOT_RUN`으로 남긴다.

### 완료 조건

- T01\~T10의 해당 필수 검증 PASS
- 기존 P1 반례 해소
- 실제 App Server 종료 확인
- Reader·Writer 기존 동작 보존
- 제품에 검증 전용 기능 추가 없음

## 6. S4 — 실제 일반 Codex 개발 작업 검증

**이번 작업의 핵심 수용 단계**

기존 Codex 도구와 Reader·Writer만 사용한다. 새로운 검증 전용 제품 기능을 만들지 않는다.

### S4-A — 실제 Luna Reader 직접 실행

먼저 기존 Reader CLI에서 확인한다.

- 실제 Luna 요청·해결 모델 일치
- 정상 Turn 완료
- 대형 참조 파일 처리
- 짧은 결과 반환
- 사용량 기록
- 서버 종료·drain 확인

직접 호출은 일반 세션 검증의 선행 확인이며, 최종 완료 증거를 대신하지 않는다.

### S4-B — 일반 Codex Reader 위임

격리된 시험 프로필 또는 명시적 시험 범위에서 Reader Hook을 검증한다.

기존 계정의 기본 채택 정책은 변경하지 않는다.

**실제 개발 작업 흐름**

1. 원래 개발 과제와 수용 조건을 사전에 고정
2. 주 모델이 큰 파일을 읽으려는 상황 발생
3. Reader Hook 발동
4. Luna가 원본 파일을 읽고 질문에 답변
5. 주 모델에 짧은 결과 전달
6. 주 모델이 결과를 사용해 원래 개발 과제 구현
7. 실제 프로젝트 테스트와 원래 수용 조건 검증
8. 최종 과제 완료 판정

**Reader 성공 조건**

- Luna Reader 호출 성공
- 요청·해결 모델 Luna 일치
- 원본 대량 내용의 불필요한 주 모델 재전달 없음
- Luna 답변이 원래 질문에 부합
- 주 모델이 원래 개발 과제를 완료
- 동일 수용 조건과 프로젝트 검증 PASS

Luna 답변이 틀렸거나, 답변을 사용했어도 원래 과제가 실패했다면 Reader의 실사용 성공으로 집계하지 않는다.

필요한 범위 읽기·교차 검증·수정은 허용한다. 해당 비용은 사용량 계산에 포함한다.

시험 종료 후 기존 Hook 정책을 유지한다.

### S4-C — 일반 Codex Writer 위임

신규 파일을 생성하는 실제 개발 과제를 수행한다.

**실제 개발 작업 흐름**

1. 주 모델이 신규 파일의 명세·참조 경로 결정
2. 기존 Writer Skill 명시적 호출
3. Luna가 코드 생성
4. 기존 I/O 도구가 신규 파일 저장
5. 주 모델이 결과 검토
6. 필요한 부분 수정
7. 실제 프로젝트 테스트 수행
8. 원래 개발 과제 완료 판정

**Writer 성공 조건**

- 실제 Luna Writer 호출 성공
- 요청·해결 모델 Luna 일치
- 신규 파일 생성·저장 성공
- 프로젝트 테스트 및 원래 과제 수용 조건 PASS
- 주 모델이 코드 전체를 불필요하게 다시 생성하지 않음
- 생성 코드 전체가 도구 응답을 통해 주 모델에 다시 전달되지 않음

**출력 절감 검증**

반드시 다음을 구분해 기록한다.

| 관측 대상        | 확인 사항                    |
| ------------ | ------------------------ |
| Luna 출력      | 생성 코드 및 실제 output tokens |
| Writer 도구 응답 | 전체 코드가 아닌 짧은 저장 결과인지     |
| 주 모델 도구 입력   | 생성 코드 전체의 재전달 여부         |
| 주 모델 출력      | 코드 전체의 불필요한 재생성 여부       |
| 추가 읽기        | 필요한 부분 읽기와 검토 비용         |
| 수정·재작업       | 실제 사용량과 최종 품질            |

파일 저장이 성공해도 생성 코드 전체가 도구 응답으로 주 모델에 반환되면 **I/O 대체 성공으로 인정하지 않는다.**

다만 필요한 코드 일부 확인이나 부분 수정 자체를 실패로 처리하지 않는다. 실제 토큰·시간·검증 비용에 포함한다.

### S4 완료 조건

Reader와 Writer 모두 실제 일반 Codex 세션에서 원래 개발 과제를 완료해야 한다.

다음 증거를 확보한다.

- 실제 모델 호출 및 요청·해결 identity
- 주 모델과 Luna의 도구 입력·출력 기록
- Reader 답변 및 Writer 생성 파일
- 원래 과제의 테스트·수용 결과
- 필요한 재읽기·수정·재작업 기록
- 주 모델 대량 I/O 대체 여부

**모의 테스트 PASS나 단독 CLI 성공으로 S4를 완료 처리하지 않는다.**

### 사용량 제한 시

실제 모델 호출이 불가능하면 S4만 `외부 의존성 보류`로 표시한다.

S0\~S3에서 완료한 코드 수정·설치 결과는 유지한다.

## 7. S5 — 경제성 채택 판단 (별도 조건)

이번 결함 수정 및 실사용 검증의 필수 완료 범위에서는 제외한다.

기존 경제성 결과와 수용 기준을 유지한다.

| 항목        | 채택 기준                          |
| --------- | ------------------------------ |
| 품질        | 동일 과제 3/3                      |
| 완료당 환산 비용 | 직접 처리 대비 15% 이상 절감             |
| 완료당 시간    | 증가 25% 이하                      |
| 집계 비용     | Main + Luna + 검토 + 수정 + 실패·재작업 |
| 판단 단위     | Reader·Writer 독립 채택            |

새 A/B 비교는 경제성 재평가가 별도로 필요한 경우에만 실행한다.

실행하지 않았다면 A09를 `미검증`으로 표시하고, 기존 결과에 따른 기본 채택 보류를 유지한다.

경제성 기준 미달을 이유로 추가 아키텍처 개발을 시작하지 않는다.

**P1/P2 코드 수정 완료:** A01\~A04 PASS

**Reader 실사용 완료:** A01\~A06 및 Reader의 A08 PASS

A09가 미검증이어도 A01\~A08이 통과했다면 이번 수정 작업은 완료할 수 있다. 단, 경제성 채택 완료로 보고하지 않는다.

## 9. 실행·보고 규칙

### 작업 순서

```
S0 — P1 반례 고정
    ↓
S1 — 네이티브 직접 실행·종료 수정
    ↓
S2 — Windows 집중 회귀 및 실제 서버 종료 검증
    ↓ PASS
S3 — 계정 설치·무결성 확인
    ↓ PASS
S4 — 일반 Codex Reader·Writer 실사용 검증
    ↓
A01~A08 최종 완료 판정

S5 — 별도 경제성 채택 판단
```

S0\~S2는 하나의 개발 묶음으로 진행한다. 필수 검증을 통과하면 S3까지 연속 진행한다.

S4는 실제 모델 사용이 가능한 범위에서 진행하며, 사용량 제한으로 막히면 해당 단계의 사유와 영향을 기록하고 종료한다.

### 완료 보고 형식

새 진단 기능이나 별도 보고 플랫폼을 만들지 않는다.

기존 A01\~A09에 다음 열만 추가한다.

| ID       | 판정                              | 실행 증거 위치        | 미완료 사유   |
| -------- | ------------------------------- | --------------- | -------- |
| A01\~A09 | PASS / FAIL / NOT_RUN / BLOCKED | 실제 로그·파일·테스트 경로 | 미통과 시 기록 |

검증 증거가 없는 항목을 PASS로 표시하지 않는다.

테스트 성공, 설치 성공, 실사용 성공, 경제성 채택은 서로 다른 결과로 보고한다.

### Git 마무리

S0\~S3 필수 검증을 통과한 변경만 상세한 한국어 커밋으로 기록하고 `main`에 푸시한다.

S4가 모델 사용량으로 보류된 경우에도 검증 완료된 실행 결함 수정은 보존한다. 다만 실사용 완료로 선언하지 않는다.

## 10. 최종 종료 원칙

이 작업은 새로운 하네스 기능을 개발하는 프로젝트가 아니다.

**기존 Codex App Server 실행 결함을 수정하고, 이미 개발된 Reader·Writer가 실제 일반 Codex 작업에서 주 모델의 대량 I/O를 대체하는지 증명하는 작업이다.**

구현은 최소화한다. 검증은 실제 사용자 작업 경로까지 수행한다. 경제성은 별도 조건으로 판정한다.

## 최종 변경 요약

이번 v4는 이전 계획에서 다음 세 가지만 실질적으로 변경했습니다.

1. Reader 완료 기준 강화: Luna 답변 반환이나 개발 진행이 아니라, 원래 과제 완료와 동일한 수용 검증 통과까지 요구합니다.
2. 경제성 범위 확정: A01\~A08을 이번 작업의 필수 완료 조건으로 고정하고, A09는 독립적인 채택 기준으로 분리했습니다.
3. Writer 출력 검증 강화: 코드 재생성뿐 아니라 Writer 도구 응답으로 생성 코드 전체가 주 모델에 다시 전달되는지 확인합니다. 필요한 부분 수정과 검토는 허용하며 비용에 포함합니다.

최종 판정: v4 실행계획 확정, S0\~S2 즉시 착수 가능.

추가 계획 개정이나 아키텍처 설계는 필요하지 않습니다. 이번 응답에서는 코드·설정·Git을 변경하지 않았습니다.
