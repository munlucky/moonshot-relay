# C29 · Follow-up 비용 비교와 Adaptive 판정

Wave: W9
선행: C28
유형: 평가/판정
초기 상태: NOT_STARTED

## 목표

Adaptive 채택 여부를 evidence로 결정한다.

## 필요한 입력

- C28 전체 결과
- CONTRACTS.md의 E

공통: 해당 선행 카드 결과와 [RUNBOOK](../RUNBOOK.md)의 필요한 부분만 읽는다. 현재 원본이 바뀌었으면 경로를 재확인한다.

## 변경 범위

평가 분석과 기존 policy의 판정 문서. 새 policy 구현은 별도 작은 수정 카드.

제품 원본 2~5개와 관련 테스트 1~3개를 기본 크기로 삼는다. 구현 전에 실제 파일 목록을 checkpoint에 고정한다. 위 디렉터리명은 전체 디렉터리를 고칠 허가가 아니다. 새 파일은 기존 구조로 표현 불가능한 경우에만 추가한다.

## 이번 카드에서 할 일

F1 비용과 F2/F3 비용 및 총비용을 따로 보고한다. task 성공·회귀·scope 위반을 비용보다 먼저 판정한다. 개선이 없으면 incumbent를 유지한다.

## 완료 조건

- AC-1: 케이스별 결과와 변동 범위, 누락 데이터, 채택/보류 근거가 있다. 평가 수치만으로 Kernel 권한이 바뀌지 않는다.
- AC-2: 평균 비용 감소로 correctness 악화를 덮지 않는다. 결과를 보고 채점 기준을 바꾸지 않는다.
- AC-3: 아래 검증의 실제 결과가 현재 source/diff와 연결된다. 미실행 항목을 통과로 기록하지 않는다.
- AC-4: 변경 경로, evidenceRefs, 남은 항목, 다음 카드 ID가 checkpoint와 STATUS에 기록된다.

## 검증

집계 재현·실패 포함 여부·pairing identity·선정 기준 일치 확인.

코드 변경이면 현재 build 절차로 테스트 산출물을 갱신한다. 해당 source test를 고치고 생성 진입점을 실행한다. 기존 검사 이름은 실행 시 package/source mapping과 대조한다. 실제 command/receipt가 없는 검증 결과는 인정하지 않는다.

## 범위가 커지거나 중단될 때

다른 독립 동작, 별도 migration, 다수 owner 변경이 필요하면 C29a/C29b로 분리한다. 하위 카드에 목표·선행·허용 파일·AC·검증을 적는다. 테스트가 실패하면 원인을 분류하고 같은 범위의 수정만 수행한다. 무관한 수정은 후속 항목으로 남긴다.

재개 시 기존 taskId/operationId/sessionId와 현재 diff를 먼저 확인한다. 이미 끝난 수정이나 실행을 반복하지 않는다. 이 카드가 완료돼도 다음 카드는 자동 시작하지 않는다.
