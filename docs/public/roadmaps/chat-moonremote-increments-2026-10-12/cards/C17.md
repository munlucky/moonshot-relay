# C17 · Knowledge type 표현 가능성 판정

Wave: W4
선행: C16
유형: 기준/계약/검증
초기 상태: NOT_STARTED

## 목표

procedure를 기존 record type으로 표현할 수 있는지 먼저 판정한다.

## 필요한 입력

- src/kernel/knowledge/records.ts
- schemas/kernel.knowledge-record.schema.json
- src/kernel/knowledge/context-load.ts

공통: 해당 선행 카드 결과와 [RUNBOOK](../RUNBOOK.md)의 필요한 부분만 읽는다. 현재 원본이 바뀌었으면 경로를 재확인한다.

## 변경 범위

설계/fixture만. schema는 아직 변경하지 않는다.

제품 원본 2~5개와 관련 테스트 1~3개를 기본 크기로 삼는다. 구현 전에 실제 파일 목록을 checkpoint에 고정한다. 위 디렉터리명은 전체 디렉터리를 고칠 허가가 아니다. 새 파일은 기존 구조로 표현 불가능한 경우에만 추가한다.

## 이번 카드에서 할 일

전제·단계·검증·적용 범위·금지·유효 기간의 대표 procedure 3개를 기존 타입에 매핑한다. 알려진 실패와 episodic observation을 함께 검토한다.

## 완료 조건

- AC-1: 기존 타입으로 충족/불충족인 필드와 근거가 있다. 새 generic procedure 필요 여부가 명시된다.
- AC-2: 표현이 가능하면 새 type을 만들지 않는다. 여러 전용 procedure 종류를 만들지 않는다.
- AC-3: 아래 검증의 실제 결과가 현재 source/diff와 연결된다. 미실행 항목을 통과로 기록하지 않는다.
- AC-4: 변경 경로, evidenceRefs, 남은 항목, 다음 카드 ID가 checkpoint와 STATUS에 기록된다.

## 검증

fixture round-trip과 retrieval 관점 검토. 실제 source validator를 사용한다.

코드 변경이면 현재 build 절차로 테스트 산출물을 갱신한다. 해당 source test를 고치고 생성 진입점을 실행한다. 기존 검사 이름은 실행 시 package/source mapping과 대조한다. 실제 command/receipt가 없는 검증 결과는 인정하지 않는다.

## 범위가 커지거나 중단될 때

다른 독립 동작, 별도 migration, 다수 owner 변경이 필요하면 C17a/C17b로 분리한다. 하위 카드에 목표·선행·허용 파일·AC·검증을 적는다. 테스트가 실패하면 원인을 분류하고 같은 범위의 수정만 수행한다. 무관한 수정은 후속 항목으로 남긴다.

재개 시 기존 taskId/operationId/sessionId와 현재 diff를 먼저 확인한다. 이미 끝난 수정이나 실행을 반복하지 않는다. 이 카드가 완료돼도 다음 카드는 자동 시작하지 않는다.
