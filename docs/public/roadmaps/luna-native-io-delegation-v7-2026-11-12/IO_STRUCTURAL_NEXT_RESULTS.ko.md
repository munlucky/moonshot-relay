# Luna I/O 구조 후보 N1–N3 검증

2026-11-13. 기준은 `a20985151ac980ff89e4ffce650db265746c9a66`이다. 별도 작업 트리에서 후보를 하나씩 적용했다. 세 후보 중 반복 채택 검증으로 넘길 만큼 품질과 비용 효과가 확인된 범위는 없었다. 계획에 따라 첨부된 검토 채팅에 새 구조 후보를 요청했다.

## 비교 조건

- Main은 GPT-6.1 Sol/high, I/O는 기존 Host 정책의 GPT-6 Luna/medium이다. Main은 자연어 요청을 받고 도구 인자 또는 CLI stdin JSON을 준비했다. 모델과 노력 수준은 매 실행에서 검사했다.
- 첫 호출 전에 선별 과제, 순서, 입력 해시, 품질 기준, 18회 선별 상한과 $12 API 환산 비용 상한을 등록했다. 실행마다 임시 Main 세션을 사용했다. N1은 이미 열린 세션에서 별도 Reader 연결 비교도 수행했다.
- 백만 토큰당 비캐시 입력·캐시 입력·출력은 Sol $2/$0.10/$10, Luna $0.10/$0.01/$0.50이다. 실제 구독 차감액은 측정하지 않았다. [OpenAI API 가격](https://developers.openai.com/api/docs/pricing)
- 표의 금액은 Main 턴 종료까지 관측한 합계다. 추가 확인이 포함될 수 있으므로 직접 비교에 앞서 도구 호출, 수신 직후 사용량, 후속 작업을 따로 검사했다. 수신 직후 값은 이벤트 순서에서 식별 가능한 경우의 근사치다. Main의 실제 내부 수신 순간을 직접 계측한 값은 아니다.
- Writer 파일은 기존 외부 Node 검사를 사용했다. Reader의 첫 답과 최종 전달을 별도로 대조했다. 한도에 걸린 N3 시도 4건은 Model usage 미관측으로 기록했다. 한도 해제 뒤 동일 과제를 다시 실행했다. 한도 실패는 후보 성공률과 별도로 보존했다.

N1은 Codex 0.162.1의 공식 MCP stdio 경로에서 두 도구를 등록하고 실제 호출했다. 고정 작업 디렉터리를 사용했다. 도구 인자로 루트를 주거나 상위 디렉터리를 참조하는 요청, 기존 파일과 잘못된 예산을 검사했다. 대표 Reader의 이점은 이미 열린 세션에서 재현되지 않았다. 두 Writer 결과의 방향도 갈렸다. [Codex MCP 설정](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

N2는 원문 범위, CRLF 보존, 출력 예산, 참조 변경 및 오류 시 답 보존을 로컬 검사에서 확인했다. 첫 유료 버전은 CRLF 행 끝에 CR을 남겼다. 수정 버전의 로컬 검사는 통과했다. 유료 과제는 LF였고 이 수정은 해당 과제의 잘못된 범위 선택을 바꾸지 않는다.

N3는 같은 후보 저장 경로에서 본문만 쓰고, 앞에 코드 펜스가 붙은 출력, 초과 바이트, 참조 변경을 거부하는 것을 확인했다. 중간 파일의 Luna 출력은 141 → 74토큰이다. C0 추론 36개를 빼면 가시 출력은 105 → 74토큰이다. 그 차이의 단가는 $0.00001550이다. 수신 근사 총비용에서 관측된 12.8% 차이 중 대부분은 Main 사용량 차이다. Main에서 2,128개 비캐시 입력 감소가 있었고 N3의 출력은 38개 늘었다. 후보는 Writer 출력 형식만 변경하므로 이 차이를 형식의 효과로 귀속할 근거가 없다. 큰 파일에서 양쪽 모두 기존 결과를 다시 생성했고 N3 전체 턴 비용이 40.1% 높았다. 큰 파일의 최종 외부 검사는 첫 저장 파일을 소급 검증하지 않는다.

C0의 초기 안내에서 예산 필드의 위치가 모호했다. Main은 6회 모두 중첩 객체를 사용했고 기존 CLI가 요청을 거부했다. 비용은 적용 경로 $0.108451, 승격 및 롤백 $0.125075였다. 별도로 최상위 필드 이름을 명시해 과제당 한 번 확인했다. 두 요청 모두 답과 출처를 전달했고 $0.017440, $0.021271이었다. 두 성공을 원래 반복군에 합치지 않았다. 이 대조에서 N5보다 C0가 저렴했다.

## N6 · 새 Writer 과제 반복 검증

라벨 집계와 정렬된 이벤트 병합 과제에서 Main 직접, 설치된 Native Writer, 기존 Standalone CLI, N6를 각각 세 번 교차 실행했다. Main은 사용자 설정인 Sol/high를 사용했다. Luna는 medium이다. 대상 경로, 참조, 명세와 외부 검사 기준을 실행 전에 고정했다.

표는 전체 시도 비용을 성공 수로 나눈 USD다. 괄호 안은 캐시 입력을 일반 입력으로 환산한 보조값이다. 관측값은 Main 최종 전달까지 포함한다.

| 과제 | 직접 A | Native B0 | CLI C0 | N6 |
| --- | ---: | ---: | ---: | ---: |
| 라벨 집계 | 3/3 · 0.044158 (0.215047) | 3/3 · 0.058059 (0.333727) | 3/3 · 0.036297 (0.287949) | 3/3 · 0.028428 (0.100679) |
| 이벤트 병합 | 3/3 · 0.053299 (0.237077) | 3/3 · 0.066637 (0.390316) | 2/3 · 0.110776 (0.715920) | 3/3 · 0.026691 (0.104151) |
| 합계 기준 | 6/6 · 0.048729 (0.226062) | 6/6 · 0.062348 (0.362022) | 5/6 · 0.066089 (0.459137) | 6/6 · 0.027559 (0.102415) |

N6의 성공당 비용은 Native보다 55.8%, 직접보다 43.4%, CLI보다 58.3% 낮았다. Native 대비 과제별 절감은 51.0%와 59.9%다. 캐시를 일반 단가로 환산해도 Native보다 71.7% 낮았다. N6는 6/6에서 Main 요청 2회, Luna 생성 1회, 일반 도구의 적용 1회였다. 대응 Main 요청 범위는 직접 4–5회, Native 5–8회, CLI 3–10회였다.

라벨 집계의 첫 CLI는 같은 회차의 N6보다 저렴했다. 이벤트 병합의 첫 CLI는 소비자 조기 종료 때 열린 반복자 두 개를 닫지 않았다. 비용은 합산했고 실패는 성공 수에서 제외했다. 실행 기록에는 지연, 토큰, 생성 파일 바이트와 실패 검사가 있다. 24회 전체 API 환산 비용은 $1.162259다. 실제 구독 차감액은 측정하지 않았다.

직접과 Native는 일부 시도에서 저장 후 자체 확인을 수행했다. 표의 최종 응답까지 비용에 포함된다. Native의 마지막 기다림 결과를 소비하는 첫 Main 요청까지로 잘라 추정하면 성공당 $0.046042로 N6가 40.1% 낮다. 직접에서 자체 확인 뒤의 마지막 Main 응답을 통째로 빼는 보조 계산에서는 $0.044764로 N6가 38.4% 낮다. Native 추정은 이벤트 순서로 관측한 전달 근사치다. 직접 보조 계산은 필요한 최종 전달까지 빼므로 원래 지표와 다르다. 자체 확인을 절감률의 유일한 원인으로 보기 어렵다.

별도 Terra/high 실행 1회에서 Luna/medium 선택과 Main 2회·적용 1회를 확인했다. 생성 파일은 입력 반복자가 예외를 던질 때 열린 왼쪽 반복자를 닫지 않아 외부 검사에 실패했다. 비용 $0.017828을 별도 보존했다. 사용자가 다른 Main 검증이 불필요하다고 지시했다. Sol 판정에 합산하지 않았고 추가 실행을 종료했다.

**판정.** 사용자 Main 설정에서 명시한 신규 파일 Writer는 반복 품질과 비용 조건을 통과했다. Reader는 현재 경로를 유지한다. 실험 당시에는 제품 적용을 보류했다. 기준 패키지 표면이 기존 한도를 파일 146개와 1,792,950바이트 초과하고, 실험 훅은 제한된 sandbox별 동작과 설치·갱신·복구 경로를 검증하지 않았다. 계정 설정 및 설치된 두 Skill 해시는 모든 실행에서 최초와 일치했다. 공유 라우터나 패키지 예산 변경 없이 실험 코드를 보존했다.

Git 반영에서는 명시 Writer 훅과 기존 적용 명령을 제품 코드에 연결했다. 계정 루트 설치는 별도 작업이다.

제품 반영 검증에서 Standalone·설치 12건, 카탈로그·패키지 생성 23건이 통과했다. 최종 Writer 훅은 검증된 Full Access 권한 모드에서 후보를 준비한다. 실제 대상 생성은 일반 도구의 io-apply로 수행한다. 현재 패키지 크기 기준선 실패는 별도로 남아 있다.

Kernel 소스 런타임 검증의 첫 실행은 개별 검사 18개를 통과한 뒤 지정한 240초 제한에 걸렸다. 테스트 오류 없이 시간 제한으로 종료됐으며 제한을 늘려 후속 검증을 수행했다.
